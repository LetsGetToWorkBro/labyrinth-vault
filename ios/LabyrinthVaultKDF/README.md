# The native primitives

Two of them, and they are here for opposite reasons. `Argon2id.swift` is a
second implementation of something with an external specification, ported
because JavaScriptCore is too slow to run the first one. `CryptoNight.swift`
is a thin wrapper over somebody else's C, vendored because there is no second
implementation worth having and no way to open a Monero wallet without it.
The rest of this file is the first; the second is at the bottom.

## What is settled

`Argon2id.swift` derives keys through the vendored Argon2 reference C and
reproduces `test/fixtures/primitives.json` exactly. That is the same file
`test/primitives.test.ts` holds the TypeScript to, generated by argon2-cffi,
which wraps the Argon2 reference C. Neither of our implementations is the
oracle for the other; both answer to a third one that has never seen this
repository. `swift test` runs it inside `npm test`.

The measurement that motivated the port, next to the one that closes it:

    Argon2id, t=3 m=64MiB p=1, dkLen=32

      JavaScriptCore on an iPhone 17 Pro Max      ~67 s     (measured, build 3)
      libsodium on this build machine             ~0.16 s

Different hardware, so not a ratio to quote. What it establishes is that the
cost is the interpreter rather than the algorithm, which is the thing the
41x analogy in docs/native-primitives.md could only suggest.

## How a phone gets it

By compiling it. `vendor/argon2` is C source in this repository, built by the
same target on Linux, on a Mac and on a phone, so there is no platform where
this works and another where it has to be arranged. That was the open half of
step 1 and it is closed.

The first version of this file used libsodium through a `.systemLibrary`
target, which reached apt here and Homebrew on a Mac and could never have
reached iOS at all. Replacing it removed a dependency rather than adding one.

Speed did not pay for the change, which is worth recording because it was the
obvious worry:

    Argon2id, t=3 m=64MiB p=1, dkLen=32, on this build machine

      libsodium                         0.156 s
      vendored reference C, release     0.189 s
      vendored reference C, debug       1.024 s

The third row is the one to watch. `swift test` builds the C at `-O0` by
default, so a timing taken from an ordinary test run is about five times
pessimistic and says nothing about the app.

## What libsodium could not compute, and this can

`crypto_pwhash` is not general-purpose Argon2id. It fixes the salt at
`crypto_pwhash_SALTBYTES` and fixes parallelism at one. `SALT_BYTES` in
`src/keys/seal.ts` is 16 and matched; `KDF_LIMITS.maxP` is 4 and did not. So a
blob this format permits could not have been derived natively, and the native
path would have had to hand those back to JavaScript.

The reference C has neither restriction, and the tests check both directly: a
17-byte salt against its published vector, and `p = 4` asserted to produce a
different key from `p = 1`. That second one matters more than it looks. A
wrapper that quietly ignored `p` would return the `p = 1` key, the vault would
not open, and nothing would say why.

The JavaScript path still stays in the build and is still tested. That is step
4, and it is now a genuine cross-check of two implementations rather than a
fallback carrying cases the fast path could not do.

# CryptoNight, which is a different kind of thing

Everything above is about a primitive with a public specification and vectors
from a third party, ported so that two implementations check each other.
`CryptoNight.swift` is none of that and the difference matters, so it gets its
own heading rather than a paragraph.

## Why it is here at all

Monero's `wallet2` encrypts an exported key-image set with ChaCha20, under a
key it gets by hashing the view secret key with CryptoNight: the retired
proof-of-work function, used as a KDF over a value that was already uniformly
random.

    crypto::generate_chacha_key(&view_secret_key, 32, key, kdf_rounds)
      -> cn_slow_hash(data, 32, out, variant 0, prehashed 0, height 0)

`src/crypto/chacha.h`, and `wallet2.cpp:15510`. There is nothing to like about
that choice and nothing to be done about it: it is the file format. Cake
Wallet, Feather and monero-cli interoperate on key images because all three
link this same C and get the same 32 bytes out of it.

## Why it was vendored rather than written

The Argon2id argument does not carry over. That port is defensible because RFC
9106 publishes vectors from an implementation neither of ours had seen, so
each side answers to something external. CryptoNight has four vectors in
`tests/hash/tests-slow.txt` and otherwise only Monero's source as its
specification. A TypeScript CryptoNight would be a thousand lines of
scratchpad indexing checked by nothing. It would match four inputs or be wrong
on the fifth, and the fifth would be a real wallet.

So `vendor/cryptonight` is Monero's C at tag `v0.18.5.1`, at its own paths, so
that `diff -r` against a checkout of that tag is the whole audit. Thirty-one
files are upstream's. Three are ours, and `MANIFEST.json` names them:

    include/labyrinth_cryptonight.h        the two functions Swift may call
    shim/labyrinth_cn.c                    binds variant 0; stubs the JIT and RandomX
    shim/boost/preprocessor/stringize.hpp  fourteen lines, so warnings.h resolves

## What was narrowed on the way in

`cn_slow_hash` takes a variant argument that selects five different hash
functions. The C entry point takes no variant argument, so nothing in Swift
can ask for another one. `CryptonightR_JIT.c` is not vendored at all: it writes
machine code into an mmap'd page, which iOS forbids third-party apps outright.
Its symbol resolves to a stub that aborts. RandomX is not vendored either.

`NO_AES` picks the portable C over the AES-NI and NEON implementations inside
the same file. All three compute the same four vectors; the portable one means
Linux CI runs the code the phone runs, which the ARM path could never claim.

    cn_slow_hash over 32 bytes, on this build machine

      AES-NI build                        27 ms
      portable build (NO_AES), shipped    50 ms

Once per key-image export, so the 23 ms buys a code path that is checkable
here. `FORCE_USE_HEAP` is not a preference: the portable path otherwise
declares its 2 MiB scratchpad as a stack array and an iOS thread has 512 KiB.

## What the tests do and do not prove

`CryptoNightVectorTests` runs the four vectors from `tests/hash/tests-slow.txt`
at the pinned tag. Those are Monero's own answers, so this is not the
cross-implementation check `Argon2idVectorTests` is, and the file says so at
the top. What it does catch is what actually goes wrong with vendored C: an
incomplete file set, a build linked against something that returns zeroes, a
define that silently selected a different implementation, and a Swift boundary
that passes the wrong length or a null pointer.

One thing not claimed. The secret is wiped on our side of the call: the input
copy and every intermediate round, through Monero's own `memwipe`. It is not
wiped inside the vendored code, whose 2 MiB scratchpad and working state are
upstream's stack and heap. Reaching into those would mean editing files this
repository pins byte for byte. Better said plainly than implied away.
